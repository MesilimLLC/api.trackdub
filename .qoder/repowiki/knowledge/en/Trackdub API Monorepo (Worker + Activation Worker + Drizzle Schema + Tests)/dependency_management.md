## Approach

This is a single-package Node.js monorepo managed with **Bun** as the package manager. `package.json` declares `"packageManager": "bun@1.4.0"`, which pins the toolchain version, and `bun.lock` is the committed lockfile (lockfileVersion 3). There are no sub-workspaces — all dependencies live in the root.

The runtime targets Cloudflare Workers via Hono + Wrangler; development/test uses the `@cloudflare/workerd-linux-64` binary and `@cloudflare/vitest-pool-workers` to run Vitest inside the real `workerd` runtime.

## Key Files

- `package.json` — dependency declarations, scripts, `allowScripts`, and `overrides`.
- `bun.lock` — deterministic lockfile produced by Bun.
- `.npmrc` — sets `legacy-peer-deps=true` so Bun ignores peer dependency resolution conflicts.
- `scripts/gen-docs-rag-pin.mjs` — generates `src/docs-rag/pin.generated.ts` from a JSON pin file; invoked via `gen:docs-rag-pin` / `check:docs-rag-pin` / `predev:docs-rag` / `predeploy:docs-rag` scripts.

## Versioning Strategy

- Most direct runtime dependencies use **caret ranges** (`^0.45.2`, `^4.13.8`, `^3.25.0`) allowing minor/patch bumps.
- A subset of packages is **pinned to exact versions**: `better-auth` `1.6.25`, `@modelcontextprotocol/client` `2.0.0`, `@modelcontextprotocol/sdk` `1.30.0`, `@modelcontextprotocol/server` `2.0.0`, `@cloudflare/workerd-linux-64` `^1.20260731.1`, `@cloudflare/workers-types` `5.20260922.1`. The MCP SDK ecosystem is pinned tightly across client/sdk/server.
- `bun.lock` is checked into the repo, so CI and local installs resolve deterministically from it.

## Transitive Dependency Control

- `overrides` section forces `@modelcontextprotocol/sdk`'s transitive `zod` dependency to exactly `3.25.76`, overriding whatever range its own `package.json` requests. This is the only explicit override in the project.
- `.npmrc` enables `legacy-peer-deps=true`, which tells Bun to ignore peer dependency mismatches rather than failing install — used here because the `cf` CLI and other dev tools declare peers that don't align with the runtime deps.

## Script-gated Provenance Pins

`scripts/gen-docs-rag-pin.mjs` reads a JSON manifest of docs sources and writes `src/docs-rag/pin.generated.ts` containing an array of `{ name, sha }` entries plus a `SYNCED_AT` timestamp. It is wired into:

- `gen:docs-rag-pin` / `check:docs-rag-pin` (manual).
- `predev:docs-rag` and `predeploy:docs-rag` (automatic before running/deploying the docs-rag worker).

This ensures the generated pin file is regenerated whenever source files change, and can be validated against the committed version via `--check`.

## Allowed Native Scripts

Because several dependencies ship native binaries or post-install scripts, `package.json` includes an `allowScripts` block explicitly whitelisting:

- `esbuild`
- `workerd`
- `sharp`
- `@cloudflare/workerd-linux-64` and `@cloudflare/workerd-windows-64`
- `es5-ext@0.10.64`

This is Bun's mechanism for permitting pre/post-install scripts on a per-package basis.

## Conventions and Constraints

- The package manager is declared and enforced via the `packageManager` field in `package.json` (`bun@1.4.0`).
- All dependency versions flow through `package.json`; there is no vendored `node_modules` tree committed.
- Deterministic installs are ensured by committing `bun.lock`.
- Peer dependency conflicts are tolerated globally via `.npmrc` `legacy-peer-deps=true`.
- Transitive `zod` versions are centrally overridden through `overrides` in `package.json`.
- Native script execution is gated through the `allowScripts` map in `package.json`.
- Docs-RAG provenance pins are auto-regenerated by the `gen:docs-rag-pin` script and guarded by `--check`.
